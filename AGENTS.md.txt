# Gym Diary — AGENTS.md

## Objetivo del proyecto

Gym Diary es una aplicación personal para registrar entrenamientos de gimnasio.

El usuario final es inicialmente una sola persona. La aplicación debe funcionar principalmente en iPhone y también poder utilizarse desde PC.

No se pretende publicar inicialmente en App Store ni pagar por distribuirla. El objetivo posterior es convertirla en una PWA instalable desde Safari en iPhone.

## Stack

- Angular 22.2
- TypeScript
- CSS
- Node.js 24
- npm 11
- Supabase
- PostgreSQL
- Supabase Auth
- Supabase Row Level Security

El proyecto Angular usa componentes standalone.

## Concepto de rutinas

El usuario cambia de rutina aproximadamente una vez al mes, pero no necesariamente en fechas exactas.

Cuando se crea/activa una nueva rutina:

- La anterior debe conservarse.
- Debe poder consultarse posteriormente.
- Los registros históricos asociados no deben perderse.

Las rutinas archivadas son principalmente de consulta.

## Entrenamientos

Un RoutineDay representa un entrenamiento dentro de una rutina.

Ejemplo:

Rutina:
- Push
- Pull
- Legs

El usuario decide desde Home cuál realizar.

## Sesiones

Una sesión representa una ejecución real de un entrenamiento.

Debe diferenciarse claramente:

- Routine = plantilla general.
- RoutineDay = entrenamiento definido en la plantilla.
- WorkoutSession = entrenamiento realizado en una fecha concreta.

Descartar una WorkoutSession NO debe eliminar el RoutineDay de la rutina.

## Historial

Los entrenamientos finalizados deben conservarse.

El historial debe permitir consultar:

- Rutina.
- Entrenamiento.
- Fecha.
- Ejercicios.
- Series.
- Peso.
- Repeticiones.

La arquitectura debe permitir posteriormente obtener progresión histórica por ejercicio.

### Relaciones conceptuales

routines
  -> routine_days
      -> routine_day_exercises
          -> exercises

workout_sessions
  -> workout_exercises
      -> workout_sets

## Usuario

Las tablas raíz se asociaron a Supabase Auth mediante user_id:

- routines.user_id
- exercises.user_id
- workout_sessions.user_id

Las tablas hijas se protegen mediante la relación con esas tablas raíz.

## RLS

Row Level Security está habilitado.

Las políticas están diseñadas para que un usuario autenticado solo pueda operar sobre sus propios registros.

No desactivar RLS como solución a errores de acceso.

Si aparece un error RLS, revisar:

- auth.uid()
- user_id
- sesión actual
- INSERT/UPDATE
- relaciones
- políticas

## Seguridad

NUNCA incluir en Angular:

- Database password
- service_role key
- Supabase secret key

Angular debe utilizar únicamente:

- Supabase Project URL
- Publishable key

La seguridad debe depender de Auth + RLS.

## Datos históricos

Una consideración importante es que modificar una rutina futura no debe alterar la representación histórica de entrenamientos ya realizados.

Por eso workout_sessions/workout_exercises deben conservar datos snapshot cuando sea necesario, por ejemplo:

- routine_name
- day_name
- exercise_name
- muscle_group
